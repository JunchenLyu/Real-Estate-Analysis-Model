系统优化路线图（Roadmap）

中国房地产产业链波动分析金融智能体 · 2026-09-26 体检报告 全部为待办建议，尚未实施任何一项。圈定范围后逐项执行。

一、模型与算法层（学术含金量最高）

1.1 A 矩阵时变性分析 ⭐⭐⭐

  • 现状：固定使用 2023 年 A 矩阵，冲击传导系数不变
  • 方案：利用已有 2002-2023 共 8 张北京投入产出表，支持多年份对比——房地产乘数的时序演变（2002 vs 2012 vs 2023）本身即是研究结论
  • 价值：答辩学术亮点；数据已在手（2017/2023 提取脚本已验证）

1.2 Ghosh 供给侧模型 ⭐⭐

  • 现状：仅有 Leontief 需求侧冲击 dX = (I-A)⁻¹ dY
  • 方案：新增 Ghosh 模型（供给侧 X = V(I-A)⁻¹），分析"水泥涨价"等成本推动型冲击，形成双模型架构
  • 工作量：约 50 行代码，文献有现成方法

1.3 风险评分权重数据化 ⭐

  • 现状：四指标线性加权（收入 30% / 债务 30% / 现金流 20% / 需求 20%），权重手设
  • 方案：换熵权法或逻辑回归确定权重；至少补权重敏感性分析
  • 价值：答辩被问"为什么权重是 0.3"时有数据依据

二、后端架构层

2.1 SQLite 持久化 ⭐⭐

  • 现状：STATE = {"reports": {}, "uploads": {}} 纯内存，服务重启即清空
  • 方案：报告/上传记录落 SQLite
  • 价值：约 2 小时工作量，消除"演示中途重启 → 历史全丢"的风险

2.2 检索结果重排（Rerank） ⭐

  • 现状：混合检索（MiniLM 语义 + bigram 关键词 RRF 融合）直接输出
  • 方案：接入 bge-reranker 本地重排
  • 代价：延迟增加 1-2 秒，需权衡

2.3 检索延迟优化 ⭐

  • 现状：单次查询 ~2.5s（8106 切片 bigram 全量扫描）
  • 方案：① bigram 倒排索引（降至毫秒级）② 热门查询嵌入缓存

2.4 LLM 输出结构强约束 ⭐

  • 现状：正则提取 JSON，偶发解析失败（已有 _enrich_report 兜底）
  • 方案：使用 response_format: json_object 强制 JSON 输出

2.5 并发保护（暂缓）

  • 多用户同时提问存在状态竞争，单人演示无影响，暂不处理

三、数据层

3.1 宏观月度序列 ⭐⭐

  • 现状：macro_history.json 仅 2015-2024 年度增速，历史对比图止于 2024
  • 方案：补统计局月度数据（销售面积/新开工/70 城房价/水泥产量），支持"领先-滞后"交叉验证

3.2 案例库扩充 ⭐

  • 现状：仅 4 个案例（日本/美国/恒大/海南）
  • 方案：补泰国 1997、香港 1997、西班牙 2008、温州 2011

3.3 债务率数据口径 ⭐

  • 现状：13 部门 debt_ratio 为经验手设值
  • 方案：替换为统计局/上市公司行业均值，或明确标注"演示口径"

四、前端层

4.1 流式输出 ⭐⭐⭐（演示体验差异最大）

  • 现状：提问后静默等待 10-30 秒，仅假动画占位
  • 方案：LLM 改 SSE 流式，工具调用轨迹实时逐条显示（"正在检索知识库…""正在运行投入产出模型…"）
  • 价值：评委观感从"等结果"变为"看 Agent 思考"，质变级提升；约半天工作量

4.2 图谱节点交互画像 ⭐⭐

  • 现状：节点仅有 tooltip 一行字
  • 方案：点击弹出侧边卡——该行业 A 矩阵列、风险评分分项、关联案例

4.3 情景对比 ⭐

  • 现状：Dashboard 仅展示最新一次分析快照
  • 方案：保存历次冲击分析（-10% / -15% / -20%），横向对比条形图

4.4 投影/窄屏适配 ⭐

  • 现状：未验证投影仪 4:3（1024×768）下的表现
  • 方案：比赛前务必实测投影效果，必要时调整字号与图表布局
